# realmlib plan — 2026-07-27

Derived from the 2026-07-27 captures: `realmproxy-swaps-chest-potions`,
`realmproxy-quest-room-claim`, `realmproxy-pets`,
`realmproxy-activate-crucible`, `realmproxy-battlepass-mission`,
`realmproxy-buy-customization-unparsed`, the 28 MB
`session-2026-07-27T16-21-06-602Z-packets` log they all slice, and the matching
appengine capture.

Ordering principle: **wrong beats missing**. A packet modelled incorrectly
silently corrupts data for every consumer; an unmodelled id merely fails loudly.
So everything in P0 is a correctness fix, P1 is confirmed-but-unmodelled, and P2
is speculative.

## P0 — correctness

### 0.1 `ChestRewardResultPacket` — done (`4717929`)

Was `byte + byte + int32`, inferred from one `00 01 00009414` sample. Correct
format is `short count + int32[count]`; the old model silently truncated any
multi-item grant. Landed with a two-item regression body.

Recorded here because it is the template for the rest of this list: a
single-sample inference that happens to round-trip is not evidence.

### 0.2 `ClaimMissionPacket` — name the fields, they are now known

Current model is four `unknown*` fields from one sample. Two independent sources
now resolve them:

```
C->S 163: 00000032 00000003 01 ffff
S->C 164: 01 01 0000
```

`/missions/getPlayerMissions` for the same account returns
`<TreesUnlocked>50,51</TreesUnlocked>` and, inside `<Season id="50">`, the entry
`3,4,1,1783451287,0,0`.

- `unknownInt` → `boardId` (50 = the season mission tree)
- `unknownInt2` → `missionId` (3, matching the season entry)
- `unknownByte` → `slot` (1) — **independent of `missionId`**, which the previous
  sample set could not show because both happened to be 1..3 in lockstep
- `unknownShort` → `subId`, −1

The season entry format is worth writing into the doc comment too:
`id, progress, state, startedTimestamp, claimed, claimedTimestamp` with
`state` 0 = active, 1 = complete/claimable, 2 = claimed. Mission 3 was
"Scouting the Unknown — complete 4 dungeons with difficulty 2 and above" at
progress 4, which is the reward popup in the screenshot.

Add: a `ClaimMissionResultPacket` doc noting the byte echoes the request's
`slot`, not the mission.

### 0.3 `ClaimBattlePassPacket.tier` — the doc is wrong, the code is right

New body ends `ff`, i.e. **−1**, where the previous capture had `2`. `readByte()`
is already signed so nothing breaks, but the comment ("observed 2; the
milestone/track being claimed") should say the field is signed and that −1 is a
sentinel — most plausibly "claim everything available", since one packet drew a
single `01` reply.

### 0.4 `FavourPetPacket` — right model, wrong story

The operation-discriminator design is **confirmed correct**, and it is worth
recording why, because ProdMafia went the other way and got it wrong:

```
C->S 145: 00 00000055
GET /char/list -> <FavoritePet>85</FavoritePet>
```

`0x55` = 85. If the leading byte were a count, that body would declare zero pets
and could not have set 85. Three more bodies: `00 00000001`, `00 ffffffff`
(clear), and `02 00009a0c 00000000`.

The `02` form needs its comment rewritten. `0x9a0c` = 39436 =
`Title_Inagural_Champion` in `object.xml`, and it was sent one packet after a
`RETITLE`. So this is not "a pet pair" — the byte selects a **category**
(0 = pet instance, 2 = title) and 145 is a general favourite toggle. Either widen
`FavourPetOperation` accordingly or rename the packet's members away from
`petIds`; the current `pair(firstPetId, secondPetId)` helper actively encourages
a wrong call.

Tests to add: all four bodies, plus the `/char/list` cross-check as a comment.

## P1 — confirmed structures with no model

### 1.1 `BUY_CUSTOMISATION_SOCKET` (140) — registered, no factory

Three bodies, from the full session log (the earlier slices miss them):

```
0003  00 000012cf 00   00 00001394 00   01 00003113 00
0001  00 00001026 01
0002  00 00001026 01   00 00001107 01
```

`short count`, then count × `{ byte, int32 itemType, byte }`. The framing is
certain because every type resolves in `object.xml` and no other split does:

| type | name |
|---|---|
| 0x12CF | Large Void Spirals Cloth |
| 0x1394 | Small Terminal Cloth |
| 0x3113 | High Lime Inferno Flipbook Style |
| 0x1026 | Deep Pink Clothing Dye |
| 0x1107 | Black Accessory Dye |

Caveat to write into the doc: because every type is < 65536, an
`int32 at offset 1` and a `short at offset 3` are indistinguishable here. The
int32 reading is chosen because every other customisation packet in this build
(`RESKIN`, `RETITLE`, `PET_CHANGE_SKIN_MSG`) writes item types as int32. A single
customisation type ≥ 65536 would settle it.

Model the two bytes as `unknownByte`/`unknownByte2` — do **not** guess. Observed:
leading 0,0,1 / 0 / 0,0 and trailing 0,0,0 / 1 / 1,1, i.e. trailing 1 exactly on
the two dyes. Plausible readings are socket index + category, or index +
apply/clear, and the capture cannot separate them.

### 1.2 Packet 141 — a new id

Server reply to 140, `01 0000` three times out of three. Add `PacketType`,
register as incoming, model as `byte success + short code` (the shape every other
result packet in this build uses). Named `BuyCustomisationSocketResultPacket`.

### 1.3 `ExaltationUpdatePacket` (114) — semantics, not structure

Docs landed in `4717929`. The remaining work is naming: the packet carries
**per-class power-up (stat-potion) totals**, proven by
`/account/listPowerUpStats` and `/char/list`'s `<PowerUpStats>` returning the
same eight numbers in the same order for both captured bodies, 1467-speed
outlier included. Consider a `PowerUpStatsPacket` alias export while keeping
`PacketType.EXALTATION_BONUS_CHANGED` (the id's wire name) intact, so consumers
stop reaching for it expecting exaltation data.

## P3 — hygiene

- **Enchantment stat-80 suffix.** `parseEnchantments` already preserves it as
  `suffix`. The 2026-07-27 capture shows the pattern clearly: entries with at
  least one empty slot carry a trailing `05 00`, fully-enchanted entries carry
  nothing. Record that observation in `enchantments.ts` — it is the kind of
  detail that looks like a parse bug to the next reader.
- **`validateCollectionCount` coverage.** `ChestRewardResultPacket` now uses it;
  audit the other count-prefixed readers for consistency so a corrupt length
  fails the same way everywhere.
- **Packet-map drift.** ProdMafia ships `tools/check_packet_maps.py`; wire an
  equivalent check into realmlib's test run so the two repos' id tables cannot
  silently diverge. Both currently disagree about 141 (realmlib has no entry) and
  about which packets have models.
